## 1. Текущее состояние проекта

Проект создан за время хакатона WOOFi ✖ DeFrens ✖ GoMining (активная разработка 07.10-15.10.2025) и с тех пор не развивался.

### Что есть

| Часть | Состав | Зрелость |
|---|---|---|
| Основное приложение | Java 21, Spring Boot, Jmix 2.6.2 (Vaadin), PostgreSQL, Liquibase | Каркас рабочий |
| Модель данных | `Account`, `ApiKey`, `Symbol`, `Order`, `Position`, `Bot`, `BotSettings` | Базовая, без ограничений целостности |
| Интеграция с биржей | Feign-клиенты `client/*` → Python-мост `woofipro-bridge` (FastAPI + CCXT) → Orderly Network | Работает на тестовой сети, без устойчивости к сбоям |
| Поток цен | `orderly/*`: WebSocket Orderly, тема `<symbol>@bbo` (лучшие bid/ask) | Работает, без переподключения |
| Торговый терминал | `view/trader/TraderView`: выбор аккаунта, ключа и тикера, проверка и установка плеча, рыночные и лимитные ордера, таблицы позиций и ордеров, ручное обновление статусов, закрытие позиции рыночным ордером | Прототип ручной торговли |
| Боты | Сущности `Bot` (желаемое и фактическое состояние, пульс, экземпляр-владелец) и `BotSettings` (депозит, плечо, число ордеров, процент перекрытия, процент прибыли, направление LONG/SHORT) + CRUD-экраны | Только схема данных, торговой логики нет |
| Тесты | Два отключённых ручных теста потока цен | Фактически отсутствуют |
| Инфраструктура | `docker-compose.yml` (приложение, PostgreSQL, pgAdmin, мост), `Dockerfile` из готового jar | Для локального запуска |

### Чего нет, хотя это заявлено в README

- стратегий и движка ботов (`strategy/`, `scheduler/`);
- модуля управления рисками (стоп-лосс, ограничение просадки, таймауты);
- слоя метрик (PnL, TI, задержки, проверки работоспособности);
- интеграции с Chainlink и Ethers.js;
- режима симуляции и тестов на исторических данных;
- CI/CD.

Параметры `BotSettings` (депозит, количество ордеров, процент перекрытия диапазона, процент прибыли) указывают на задуманную **стратегию усреднения (DCA-сетка)**: базовый ордер + N страховочных ордеров, распределённых по диапазону цены, и фиксация прибыли от средней цены входа. Именно её разумно реализовать первой.

### 2.3. Качество кода и инфраструктура

- Поток цен: URL зашит в `OrderlyStreamingClient` (свойство `orderly.ws.url` игнорируется), нет переподключения после `onFailure`, `queue.add` бросает исключение при переполнении очереди, каждое сообщение пишется в журнал на уровне INFO, на каждую вкладку браузера открывается отдельное WebSocket-соединение (`OrderlyStreamingMultiClient` написан, но отключён).
- Ошибка в заполнителе: `orderly.account-id={ORDERLY_ACCOUNT_ID}` вместо `${ORDERLY_ACCOUNT_ID}`.
- `trader-view.xml` ссылается на несуществующий класс `ru.javaboys.wootify.enums.OrderType`; на `symbolEntityPicker` подписаны два обработчика.
- Мост: на каждый запрос создаётся новый экземпляр биржи и заново загружаются рынки (медленно и расходует лимит запросов), синхронные вызовы CCXT блокируют цикл событий в `async`-обработчиках, SSE-поток отдаёт `repr` словаря Python вместо JSON, эндпоинт `/ohlcv` описан в README, но не реализован, нет повторов и ограничения частоты.
- Опечатки в схеме БД: `OVERLAP_PERSENT`, `PROFIT_PERSENT`.
- Нет `@Transactional` и планировщиков, нет автотестов, нет CI.
- `Dockerfile` требует заранее собранного jar, в `docker-compose.yml` зашит IP `192.168.88.151`.
- README описывает несуществующую структуру каталогов.
- Зависимости не обновлялись около года (Jmix, Spring Cloud, CCXT); API Orderly за это время могло измениться.

## 3. Видение продукта

**Wootify** - самостоятельно разворачиваемая платформа для автоматической торговли бессрочными фьючерсами (perpetual) на WOOFi Pro / Orderly Network, в которой:

1. торговые боты работают круглосуточно и переживают перезапуски без потери состояния;
2. любая стратегия проходит путь «тест на истории → бумажная торговля → тестовая сеть → основная сеть» на одном и том же коде;
3. каждое торговое действие проходит через независимый модуль контроля рисков;
4. оператор в любой момент видит состояние ботов, позиций и PnL и может мгновенно всё остановить.

Целевой пользователь на ближайший год - сама команда и небольшой круг трейдеров, разворачивающих систему у себя. Многопользовательский облачный сервис - за пределами горизонта этой карты.

## 4. Ключевые архитектурные решения

### 4.1. Абстракция шлюза биржи

Ввести интерфейс `ExchangeGateway` (размещение и отмена ордеров, запрос ордеров, позиций, баланса, плеча, метаданных рынков, подписки на цены и собственные исполнения). Всё остальное приложение работает только через него. Реализации:

- `BridgeExchangeGateway` - поверх текущего Python-моста (переходный вариант);
- `OrderlyExchangeGateway` - нативный Java-клиент REST и WebSocket Orderly (целевой вариант);
- `SimulatedExchangeGateway` - симулятор для бумажной торговли и тестов на истории.

### 4.2. Мост на Python или нативный клиент

**Рекомендация: перейти на нативный Java-клиент Orderly** к версии 0.4 и вывести мост из эксплуатации.

Доводы:
- исчезает второй стек (Python, CCXT) и лишний сетевой переход с секретами;
- приватные WebSocket-потоки Orderly (отчёты об исполнении, изменения позиций и баланса) дают события в реальном времени вместо опроса;
- подпись запросов Orderly (ed25519) реализуется на Java стандартными средствами (JDK 15+ или BouncyCastle);
- полный контроль над ограничением частоты, повторами и идемпотентностью.

До перехода мост дорабатывается минимально (раздел 6, этап 1), чтобы не блокировать остальную работу. Перед решением нужен короткий технический эксперимент (1-2 дня): подписанный запрос баланса и размещение ордера на тестовой сети из Java.

### 4.3. Модель исполнения ботов

- `BotSupervisor` (планировщик) сравнивает `desiredState` и `runtimeState` каждого бота и запускает или останавливает его.
- Бот захватывает аренду (`ownerInstance` + время пульса) через блокировку в БД, поэтому при нескольких экземплярах приложения бот исполняется ровно в одном.
- Бот - конечный автомат, всё его состояние хранится в БД, после перезапуска он восстанавливается сверкой с биржей.
- Стратегия - подключаемый интерфейс `Strategy` (реакция на цену, исполнение ордера, таймер), который выдаёт намерения (`place`, `cancel`, `close`), а не вызывает биржу напрямую. Намерения проходят через `RiskManager` и только затем уходят в `ExchangeGateway`.

```
 Цены / исполнения ─► Strategy ─► намерения ─► RiskManager ─► OrderExecutor ─► ExchangeGateway
        ▲                                                           │
        └────────────── сверка состояния (Reconciler) ◄─────────────┘
```

### 4.4. Работа с деньгами

Все суммы, цены и количества - только `BigDecimal`; округление до шага цены и лота из метаданных рынка; проверка минимальной стоимости ордера и максимального плеча до отправки.

## 5. Дорожная карта по версиям

Оценки даны для команды из 3-4 человек с частичной занятостью и уточняются после каждого этапа.

| Версия | Этап | Длительность | Результат |
|---|---|---|---|
| 0.1 | Хакатон (выполнено) | - | Прототип терминала ручной торговли |
| **0.2** | Стабилизация и безопасность | 2 недели | Безопасная сборка, CI, исправлены известные ошибки, актуальный README |
| **0.3** | Надёжное торговое ядро | 4 недели | `ExchangeGateway`, жизненный цикл ордера, автоматическая сверка, корректный учёт позиций и PnL, зашифрованные секреты |
| **0.4** | Движок ботов (MVP) | 5 недель | DCA-бот на тестовой сети работает сутками, переживает перезапуск; нативный клиент Orderly |
| **0.5** | Риски, симуляция, тесты на истории | 5 недель | Модуль рисков с аварийной остановкой, бумажная торговля, тесты стратегий на истории с отчётом |
| **1.0** | Готовность к основной сети | 3 недели | Наблюдаемость, оповещения, резервные копии, документация по эксплуатации, торговля малым капиталом |
| 1.x | Развитие | по мере сил | Новые стратегии, графики в терминале, Telegram-бот, REST API, роли пользователей |

Итого до версии 1.0 - около **4-5 месяцев**.

### Контрольные точки

- **КТ-1 (конец 0.2):** CI зелёный, в истории репозитория нет секретов, приложение поднимается одной командой `docker compose up` из чистого клона.
- **КТ-2 (конец 0.3):** ордер, выставленный из терминала, сам доходит до конечного статуса, позиция и PnL совпадают с данными Orderly без ручных нажатий.
- **КТ-3 (конец 0.4):** DCA-бот 72 часа работает на тестовой сети без вмешательства, включая принудительный перезапуск приложения посреди цикла.
- **КТ-4 (конец 0.5):** стратегия проходит тест на истории и неделю бумажной торговли, аварийная остановка закрывает всё менее чем за 5 секунд.
- **КТ-5 (1.0):** две недели в основной сети с ограниченным капиталом без инцидентов, оповещения доходят.

## 9. Метрики успеха

**Технические**
- доля ордеров, дошедших до конечного статуса без ручного вмешательства: ≥ 99,9 %;
- время от сигнала стратегии до подтверждения биржей: медиана < 500 мс;
- время восстановления бота после перезапуска: < 60 с;
- покрытие тестами торгового ядра и стратегий: ≥ 70 %.

**Торговые** (измеряются на бумажной торговле и тестовой сети до перехода в основную)
- максимальная просадка в пределах заданного лимита во всех прогонах;
- положительный результат после комиссий и фандинга на тесте на истории не менее чем за 3 месяца данных;
- отсутствие срабатываний аварийной остановки по причине ошибок кода.
