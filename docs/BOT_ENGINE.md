# Движок торговых ботов: архитектура и план разработки

Документ описывает, как устроен запуск торговых ботов в Wootify, и фиксирует план работ по созданию рабочего прототипа.
Общая дорожная карта проекта: [ROADMAP.md](ROADMAP.md).

## 1. Цель прототипа

Получить систему, в которой:

1. торговый бот - это поток на бэкенде со своим жизненным циклом, настройками и историей;
2. ботов можно создавать, настраивать, запускать и останавливать из UI;
3. в UI видно состояние каждого бота: работает ли он, чем занят, когда последний раз подавал признаки жизни;
4. если бэкенд упал или перезапустился, все боты, которые должны работать, продолжают работу с того же места;
5. видны ошибки и причины, по которым бот не работает;
6. первая стратегия - усреднение (DCA-сетка), которую задумывала команда;
7. бота можно гонять без реальных денег: режим бумажной торговли на живых ценах Orderly.

## 2. Принципы

- **Желаемое состояние в БД - источник правды.** Пользователь меняет только желаемое состояние (`RUNNING`/`STOPPED`), движок приводит к нему фактическое.
- **Всё, что нужно для продолжения, хранится в БД.** Состояние цикла, ордера, их идентификаторы на бирже. В памяти - только ссылки на запущенные потоки.
- **Повтор безопасен, а не невозможен.** Каждый ордер сначала записывается в БД с детерминированным `clientOrderId`, потом отправляется на биржу. После сбоя в любой точке бот находит ордер на бирже по этому идентификатору или безопасно отправляет его повторно.
- **Внешние вызовы вне транзакций БД.** Транзакции короткие: «записать намерение», «записать результат».
- **Каждый шаг стратегии идемпотентен.** Такт стратегии сравнивает план цикла с фактическими ордерами и досоздаёт недостающее. Поэтому одинаково обрабатываются и обычная работа, и восстановление после сбоя.
- **Ошибки классифицируются.** Временные (сеть, 5xx, лимиты, нет свежих цен) - повтор в том же потоке с паузой. Ошибки конфигурации - бот сразу останавливается с понятной причиной. Прочие сбои - перезапуск бота с нарастающей паузой, после исчерпания попыток - состояние `FAILED`.
- **Единоличное владение ботом.** Бота исполняет ровно один экземпляр приложения: владение оформлено арендой в БД с атомарным захватом строки.
- **Остановка кооперативная.** Сигнал остановки - в БД; флаг и прерывание потока - только ускорители.

## 3. Модель данных

| Таблица | Кто пишет | Назначение |
|---|---|---|
| `BOT` | пользователь | Конфигурация: имя, стратегия, режим (`PAPER`/`LIVE`), символ, аккаунт и ключ API, период такта, число автоперезапусков, действие при остановке. Версионируется, изменяется только у остановленного бота |
| `DCA_SETTINGS` | пользователь | Параметры стратегии усреднения (1:1 с ботом) |
| `BOT_RUNTIME` | движок | Желаемое и фактическое состояние, владелец и срок аренды, пульс, счётчики тактов и перезапусков, последняя ошибка, текущее занятие, произвольное состояние стратегии (JSON). Изменяется только атомарными SQL-операциями с проверкой владельца |
| `BOT_EVENT` | движок | Журнал бота: запуск, остановка, ордера, предупреждения, ошибки со стеком. Повторяющиеся сообщения схлопываются в одну запись со счётчиком |
| `BOT_CYCLE` | движок | Цикл (сделка) DCA: номер, направление, план сетки, средняя цена, объём, цена фиксации прибыли, реализованный PnL, комиссии, причина закрытия |
| `ORDER_` | движок, терминал | Существующая таблица ордеров, дополнена ссылками на бота и цикл, `clientOrderId`, ролью ордера (базовый, страховочный, фиксация прибыли, закрытие) и режимом |
| `PAPER_ORDER` | симулятор | «Биржевая» сторона бумажной торговли: состояние ордеров симулятора |

Конфигурация и состояние разнесены по разным таблицам, чтобы редактирование бота в UI не конфликтовало с постоянными обновлениями от движка.

## 4. Жизненный цикл бота

```
               start (UI)                     поток запущен
  STOPPED ─────────────────► STARTING ─────────────────────► RUNNING
     ▲                          │                              │  │
     │ stop выполнен            │ ошибка конфигурации          │  │ сбой
     │                          ▼                              │  ▼
  STOPPING ◄───── stop (UI) ── FAILED ◄── попытки исчерпаны ─ RESTARTING
                                                               │  ▲
                                   пауза истекла, новый захват └──┘

  RUNNING ── выключение сервера ──► SUSPENDED ── старт сервера ──► STARTING
```

- `SUSPENDED` - бот остановлен штатным выключением сервера и будет продолжен при старте.
- При аварийном падении процесса состояние остаётся `RUNNING`, но аренда истекает, и бот подхватывается при старте того же или другого экземпляра. В UI такой бот подсвечивается как «нет пульса».
- `FAILED` требует ручного запуска, который сбрасывает счётчик перезапусков.

### Действия при остановке

| Действие | Что происходит |
|---|---|
| `KEEP_ORDERS` | Бот просто перестаёт работать, ордера и позиция остаются на бирже |
| `CANCEL_ORDERS` | Отменяются все активные ордера бота, позиция остаётся. При следующем запуске бот восстановит сетку |
| `CLOSE_POSITION` | Отменяются ордера, позиция закрывается рыночным ордером, цикл закрывается |

## 5. Компоненты

```
 UI (Jmix) ──► BotControlService ──► BOT_RUNTIME (desired_state)
                                            │
                     BotSupervisor (поток "bot-supervisor", раз в 2 с и по сигналу)
                       1. продлить аренду своих ботов, потерянных - остановить
                       2. остановить ботов с desired=STOPPED
                       3. захватить ботов с desired=RUNNING без владельца
                       4. сторож: предупредить о зависших ботах
                                            │
                                            ▼
                     BotRunner (поток "bot-<имя>") ── такт ──► Strategy (DCA)
                                                                  │
                         BotOrderService (запись → отправка → сверка, clientOrderId)
                                                                  │
                         ExchangeGateway ── PaperExchange (симулятор, PAPER_ORDER)
                                         └─ BridgeExchange (woofipro-bridge → Orderly)
                         MarketDataService (WebSocket Orderly, bbo, раздельно по сетям)
                         InstrumentService (шаг цены и лота, минимальная стоимость)
```

## 6. Стратегия DCA

Параметры: направление, депозит (маржа, USDC), плечо, число ордеров N (включая базовый), диапазон сетки R %, множитель объёма M, фиксация прибыли TP %, необязательный стоп-лосс SL %, максимальное число циклов, пауза между циклами.

1. Бюджет в котируемой валюте: `депозит × плечо`. Доля ордера i: `M^i / Σ M^k`.
2. Базовый ордер - рыночный. По цене его исполнения P0 строится сетка страховочных лимитных ордеров: для LONG `P0 × (1 − R × i / (N − 1))`, для SHORT зеркально.
3. Цены и объёмы округляются до шага инструмента, каждый ордер проверяется на минимальный объём и минимальную стоимость. Непроходящая конфигурация - ошибка конфигурации ещё до первого ордера.
4. После каждого исполнения пересчитывается средняя цена и выставляется (переставляется) лимитный ордер фиксации прибыли `reduce-only` по цене `средняя × (1 ± TP)`. Лимитный ордер живёт на бирже и срабатывает, даже если бот в этот момент не работает.
5. Стоп-лосс контролирует бот: при пересечении цены отменяются ордера цикла, позиция закрывается рыночным ордером.
6. Цикл закрывается, когда позиция обнулилась. Считается реализованный PnL с комиссиями, через паузу начинается следующий цикл.

## 8. Осознанные ограничения прототипа

- Стоп-лосс исполняется ботом, а не условным ордером биржи: пока бот не работает, стоп-лосс не действует (фиксация прибыли при этом действует).
- Ручные сделки по тому же символу и аккаунту, что и у LIVE-бота, нарушают его учёт позиции.
- Один экземпляр приложения - основной сценарий. Несколько экземпляров поддерживаются арендой, но ограничение частоты запросов к бирже действует в пределах одного экземпляра.
